test-lab 是單向沙盒

任何東西都可以 merge 進去測,但 test-lab 永遠不 merge 出來。上面可能混著還沒驗過、甚至最後不會出的東西。

# 想測什麼就 merge 什麼
git switch test-lab
git merge --no-ff feature/export-filter
git push                                # → 自動部 lab

# 每循環開始時重置一次,保持乾淨
git switch test-lab
git reset --hard origin/develop && git push --force
分支保護設定 test-lab 要允許 force push(才能定期重置),但不要設成任何 MR 的預設 target。有人手滑把 test-lab merge 進 develop 會很難清。
02

時間窗控制

用日曆給出判斷基準,實際擋不擋由審查者決定。有基準,「這個很急」才有得討論。

週三 PM → 週五 PM

收 feat + fix。新功能 merge 進 release 分支,發一顆 beta 進 qa。窗口 2.5 天。

週五 PM → 隔週三 AM

只收 fix。凍結 5.5 天。凍結期的 feat MR 要不要放行,由審查者判斷。

隔週三 AM

發 rc,同時開下一條 release 分支。舊分支保持乾淨到上線,新功能進新分支。

兩個階段收的東西不同,但流程完全一樣:merge 進 test-lab 自己驗 → merge 進 release 分支 → 發 beta.N 進 qa。不因為是新功能就重開分支或重置測試基準。

test-lab 這道關卡的好處是:功能可以在進 release 分支之前先驗一輪。驗壞了就不 merge,release 分支不會被污染。

03

單一循環線圖

標籤顏色 = 部署環境。identifier 只切一次(beta → rc),單向不回頭。

rc 階段不回頭 semver 的 pre-release identifier 是字母序比大小,beta < rc,同一個 patch 內發完 rc.0 就不能再回去發 beta.N。所以 rc 階段的 bug 一律發 rc.N+1 給客戶,QA 不介入。

如果修正大到需要 QA 重驗,就在同一條 release/1.0 上升 patch、切回 beta ── npm run release:beta -- patch 發出 1.0.1-beta.0,重走 qa → rc。patch 升上去了,版號沒有倒退。

這就是分支名用兩碼的原因:release/1.0 裡面跑到 1.0.3 都還合理。
04

兩條 release 分支重疊

進入 rc 之後就開新分支收新功能,舊分支保持乾淨到上線。兩條會平行存在幾天。

# release/1.0 在 rc 階段修 bug
git switch release/1.0 && git commit -m "fix: ..." && git push
npm run release:rc                                    # v1.0.0-rc.1

git switch develop     && git merge --no-ff release/1.0   # ①
git switch release/1.1 && git merge --no-ff develop       # ② 最容易漏
05

Hotfix

單一 live 網站,main 永遠等於 live 現況,所以 hotfix 直接從 main 開。版號走第三碼。

07

指令速查

package.json

"release:beta": "release-it --preRelease=beta --no-plugins.@release-it/conventional-changelog.infile",
"release:rc":   "release-it --preRelease=rc   --no-plugins.@release-it/conventional-changelog.infile",
"release:live": "release-it"

一個循環

# ── 週三 AM · 開分支 + 重置 test-lab ──
git switch -c release/1.0 develop
git push -u origin release/1.0

git switch test-lab
git reset --hard origin/develop && git push --force

# ── 窗口期 · 收 feat ──
git switch test-lab
git merge --no-ff feature/export-filter
git push                                       # → 自動部 lab,自己先驗

# 驗過了才進 release 分支
git switch release/1.0
git merge --no-ff feature/export-filter
npm run release:beta -- minor                  # v1.0.0-beta.0
git switch develop && git merge --no-ff release/1.0

# ── 凍結期 · 修 bug ──
git switch -c fix/dropdown release/1.0
git commit -m "fix: filter dropdown misaligned"

git switch test-lab && git merge --no-ff fix/dropdown && git push

git switch release/1.0 && git merge --no-ff fix/dropdown
npm run release:beta                           # v1.0.0-beta.1
git switch develop && git merge --no-ff release/1.0

# ── 隔週三 AM · 發 rc ──
git switch release/1.0
npm run release:rc                             # v1.0.0-rc.0
git switch -c release/1.1 develop              # 同時開下一輪
git push -u origin release/1.1

# ── rc 過 · 上 live ──
git switch main && git merge --no-ff release/1.0
npm run release:live -- 1.0.0                  # v1.0.0 · CHANGELOG 生成
git switch develop     && git merge --no-ff main
git switch release/1.1 && git merge --no-ff develop

# ── 觀察一天沒事 · 砍分支 ──
git push origin --delete release/1.0

砍分支前的檢查

git branch --merged develop     | grep release/1.0   # 有輸出才安全
git branch --merged release/1.1 | grep release/1.0
git tag -l "v1.0.0"

.gitlab-ci.yml · 環境路由

deploy:lab:
  rules: [{ if: '$CI_COMMIT_BRANCH == "test-lab"' }]

deploy:qa:
  rules: [{ if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+-beta\.\d+$/' }]

deploy:release:
  rules: [{ if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+-rc\.\d+$/' }]

deploy:live:
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'       # 不含後綴才上 live
      when: manual
第一顆 beta 要帶 minor 每條 release 分支的第一次發版都要寫 -- minor。release-it 看到最新 tag 是上一版的 rc.N,自己算會接錯。之後就能自動遞增。
08

容易出事的地方

  1. 忘記回補

    release 分支修完的東西沒補進 develop 或下一條 release 分支,下一版把 bug 帶回去。建議加 CI 檢查:main 有新 commit 而目標分支沒有時發警告,比人記得可靠。

  2. 平行期間的溝通

    qa 跑 1.1.0-beta.0、release 跑 1.0.0-rc.1 的時候,跟 QA 和客戶講話一定要帶版號。GitLab 的 Operations → Environments 頁面會顯示每個環境現在跑哪個版本,直接給連結最快。

  3. commit type 要照實寫

    流程上 feat 和 fix 一視同仁,但 commit message 還是要分。conventional-changelog 靠 type 分區塊,全寫 fix: 的話 CHANGELOG 只有 Bug Fixes 一節,客戶看不出這版加了什麼。

  4. 窗口最後一天不進大功能

    週五進的 feat 只被測半天。週五只進小的,或者週五進的東西週一自己在 lab 完整回歸一次再交給 QA。

  5. 破例次數要追蹤

    每個循環都有一兩次「這個真的很急」放行,那不是紀律問題,是窗口太短或週期太長。審查者連續三次覺得難判斷,就該調整窗口。

  6. test-lab 不能 merge 出來

    那條分支上可能混著沒驗過、甚至最後不會出的東西。有人手滑 git merge test-lab 進 develop,會把實驗性 commit 帶進正式流程,而且很難清乾淨。在 CI 加一條檢查:develop / release/* / main 的 MR 來源是 test-lab 就直接擋。

  7. build 產物不保證一致

    qa 和 release 是兩次獨立 build,程式碼一樣但產物不保證 byte-identical。至少要:package-lock.json commit、build 用 npm ci。真的在意的話,每次 deploy 記錄產物 hash。
